# Task 4: shadow mode + calibration harness

Commit: `0f4d1f8` feat(core): add consolidation shadow-mode dry-run and calibration CLI

## What changed

- `EntityConsolidator.consolidate(..., dry_run=True)` (consolidation.py): runs the
  identical candidate-selection/judging path as the live call — `_find_similar`,
  the threshold gate, the batched judge call, `_parse` — with two differences: the
  `settings.enabled` gate is bypassed (a project doing calibration has it off by
  definition), and `_apply` is invoked with `apply=False`.
- `EntityConsolidator._apply(..., apply: bool = True)`: same plan-then-mutate
  control flow, same phase split, same duplicate-`existing_id` collision
  resolution, same live-survivor recheck. `apply=False` swaps every write for the
  read that answers the same question the write's return value would have
  (`mark_stale`'s `WHERE stale = 0` guard → `is_entity_live`; `archive_entity`'s
  `WHERE archived_at IS NULL` guard → the entity's own pre-run `archived_at`,
  valid throughout since nothing ever writes in a dry run). `touch_entity`/
  `transfer_citations` have no read-only equivalent and simply don't run.
- `_parse` now also captures the judge's `reason` string (previously discarded);
  `_Decision` grew from `(verdict, existing_id)` to `(verdict, existing_id, reason)`.
- New `ConsolidationDecision` dataclass + `ConsolidationStats.decisions` field
  (`list[ConsolidationDecision] | None`, only ever populated on `dry_run=True`):
  per-entity `entity_id/title`, `verdict`, `existing_id/title`, `similarity`,
  `reason`. Built by `_decision_report` purely by reading the `qualifying`/
  `below_threshold`/`decisions` structures `consolidate` already produced — no
  candidate lookup or judging happens in it. Below-threshold entities are
  reported too (verdict "ADD", their near-miss similarity still shown) so a
  threshold sweep can see what it *just* missed. Judge-failure entities that
  reached the judge are tagged `reason="judge_failed"`.
- `callmem consolidate --dry-run [--threshold F] [--limit N] [--type T]` (cli.py):
  loads the project's live (non-stale, non-archived) entities, calls
  `EntityConsolidator.consolidate(..., dry_run=True)` **once per entity**, and
  prints per-decision lines (similarity + verdict + reason) plus a summary
  (DB-accurate counts by verdict, and min/median/max similarity per raw judge
  verdict). `--dry-run` is required — omitting it refuses with a message, since
  this command is a calibration preview only; there is no CLI path to run
  consolidation live outside the normal extraction pipeline.

## Why per-entity, not one call over the whole corpus batch

`EntityConsolidator` excludes every id in its own `entities` argument from that
call's candidate lookup ("batch siblings can never consolidate each other" —
correct for a live extraction batch of genuinely co-extracted new entities). If
the CLI passed its whole `--limit`-bounded corpus slice as one `entities` list,
every entity in it would be excluded from being anyone else's candidate — exactly
the near-duplicate pairs the harness exists to find (e.g. audio-converter's
title×46 mass) would never reach the judge. Calling `consolidate()` once per
entity keeps every *other* entity eligible as a candidate while still reusing the
exact same method; `--limit` bounds the resulting number of judge calls (at most
one per qualifying entity in the batch).

## Concerns / judgment calls

- **Per-entity judge calls, not one shared batch call.** As explained above,
  this is required for correctness (batch-sibling exclusion would otherwise
  blind the harness to real duplicates), but it means `--limit N` costs up to
  N separate LLM calls rather than one batched call — flag if a cheaper design
  is wanted for very large sweeps; `--limit`'s existence in the plan already
  anticipates bounding cost this way, so I read this as intentional.
- **Per-decision `verdict` is the judge's raw verdict; summary counts are
  post-collision DB-accurate counts.** These can disagree in the rare case of a
  duplicate-`existing_id` claim (two decisions naming the same existing entity):
  the losing line still shows its raw judge verdict (e.g. "UPDATE") for
  eyeballing, while `stats.updated` only counts the winner. Documented in the
  CLI's summary heading; flag if silently reconciling them would be preferred.
- `reason`'s type validation is lenient by design: a present-but-malformed
  `reason` field degrades to `None` rather than fail-opening the whole batch,
  since it's cosmetic to the decision's validity — only `new_id`/`verdict`/
  `existing_id` gate `_parse`'s fail-open contract, unchanged from before.
- No changes to repository.py — the archived/live checks needed for the
  no-write simulation were satisfiable with pure reads already exposed
  (`is_entity_live`) or the entity's own already-loaded state, so I didn't need
  to add anything there.

# Fix round 1: reporting-layer review (7 items)

Rebased onto baseline **1332** (polish round's `transferred` → `transfer_attempts`
rename and citation-stranding fix already present in the working tree). Mechanism
(dry_run flag, per-entity design) approved as-is; all fixes below are in the
reporting layer — `ConsolidationDecision`/`_decision_report` (consolidation.py)
and `consolidate_cmd` (cli.py).

## R1 (Critical) — summary overstated would-archive, mislabeled itself

Every entity is judged against every OTHER entity in the batch (that's the
per-entity design's whole point), so an n-member duplicate cluster produces n
NOOP/UPDATE decisions — the raw counts alone imply n entities would be
archived, when a live run only ever removes (n-1) at a time as they're each
submitted. Fixed two ways:
- Dropped the false "DB-accurate — after duplicate-claim resolution" heading
  (single-entity batches make cross-entity collision resolution structurally
  unreachable) and replaced it with an explicit "per-entity hypothetical
  verdict counts ... not DB-accurate archive counts" label, plus an upfront
  paragraph explaining why.
- Implemented the preferred fix: `_consolidate_collapse_clusters` (cli.py,
  pure reporting logic over the already-returned `decisions` list — no
  consolidation.py involvement) runs union-find over NOOP/UPDATE edges
  (`entity_id <-> existing_id`; CONTRADICTS excluded since it keeps both
  sides) and reports "N cluster(s) covering M entities -> an estimated N
  survivor(s)", plus each cluster's member ids. Verified against the
  reviewer's exact reproduction (3 identical entities): raw count still shows
  `NOOP (judged) 3`, but the cluster line now reads "1 cluster(s) covering 3
  entities -> an estimated 1 survivor(s)".

## R2 (Critical) — per-decision line didn't say which side dies

`_consolidate_outcome_text` (cli.py): renders "would archive X (kept: Y)" for
NOOP, "would stale Y (superseded by X)" for UPDATE, "would stale+invalidate Y
(both kept, flagged conflicting)" for CONTRADICTS — appended to every
per-decision line.

## R3 (Important) — gate similarity silently overridden by matched-pair similarity

Confirmed the bug as described: `_decision_report` set `similarity =
hits[0]["_similarity"]` then overwrote it with the matched candidate's own
score whenever `existing_id` was set, so the printed number was the gate value
for ADD rows but the matched-pair value for everything else — an apples-to-
oranges distribution. Fixed by splitting `ConsolidationDecision.similarity`
into two fields: `gate_similarity` (always `hits[0]`, what `--threshold`
actually compares) and `matched_similarity` (the specifically-named
candidate's own score, independent of rank). Both are now emitted on every
per-decision line (`[gate=... matched=...]`) and as two separate distribution
tables in the summary, clearly labeled. New test
(`test_matched_similarity_differs_from_gate_similarity_for_lower_ranked_pick`)
constructs two embedded candidates at different cosine scores and has the
judge name the lower-ranked one, asserting `gate_similarity == 1.0` and
`matched_similarity == 0.6` simultaneously.

## R4 (Important) — ADD bucket conflated three populations

`_decision_report` (consolidation.py) now tags the `reason` field with an
explicit `"below_threshold"` sentinel for never-asked entities (previously
`None`, indistinguishable from a judge that simply omitted its reason text) —
`"judge_failed"` was already distinct. `_consolidate_add_bucket` (cli.py)
buckets every decision into `ADD (judged)` / `ADD (never asked)` / `ADD
(judge_failed)` / the real verdict for non-ADD, used for both the count
summary and the two similarity-distribution tables.

## R5 (Important) — no CLI-level structural test

Added `test_cli_routes_through_the_shared_consolidate_method`
(`TestConsolidateDryRun`): patches `EntityConsolidator.consolidate` with
`autospec=True, side_effect=EntityConsolidator.consolidate` (the real method
still runs — this is a spy, not a stub) and asserts it was called exactly
once per entity in the batch, each time with `dry_run=True` and a
singleton-entity list. A hand-rolled `consolidate_cmd` reimplementation would
show `call_count == 0` and fail this test immediately.

## R6 (Important) — unguarded judge call could abort the whole sweep

Traced the actual gap: both shipped LLM clients (`OllamaClient`,
`OpenAICompatClient`) already catch `httpx.ConnectError`/`TimeoutException`/
`HTTPStatusError` internally and return `None` — but neither catches
`resp.json()` raising `json.JSONDecodeError` (e.g. a proxy/gateway returning
a non-JSON body with a 200 status). Fixed at the single shared call site —
`raw = self.llm.extract(prompt)` inside `EntityConsolidator.consolidate` —
wrapped in `except (httpx.HTTPError, json.JSONDecodeError)`, converting the
exception into `raw = None`, which already routes through the existing
fail-open path (`judge_failed=True`, every entity in that call ADDs). One fix
point benefits the live path, the dry-run path, and the CLI's per-entity
sweep loop identically, with no new branching logic. `httpx.HTTPError` matches
the same narrow-catch idiom `embeddings.py` already uses for its own network
calls (checked for precedent before choosing it). New tests: two at the
`EntityConsolidator` level (`JSONDecodeError` and `httpx.ReadTimeout` each
fail open, zero mutations, `reason="judge_failed"`), one at the CLI level
(`test_sweep_survives_a_transient_judge_error_for_one_entity`, RED-confirmed
against the pre-fix code: `ReadTimeout` propagated to `exit_code=1` with the
raw traceback) reproducing the reviewer's "entity 40/50" scenario with a
4-entity/2-pair batch where the first pair's judge call raises and the second
pair is still judged normally afterward.

## R7 (minors, bundled)

- `--limit` now `click.IntRange(min=1)`; `--threshold` now
  `click.FloatRange(min=0.0, max=1.0)` — both give click's standard
  "not in the range" `UsageError` on a bad value instead of a confidently
  wrong "everything ADD" run.
- `--limit` help text corrected to "pinned first, then most-recently-updated"
  (matches `get_entities`' actual `ORDER BY pinned DESC, updated_at DESC`).
- Replaced `MemoryEngine(db, config)` + `engine.project_id` with a direct
  `Repository(db).get_project_by_name(...)` read-only check:
  `MemoryEngine.project_id` lazily *creates* a project row on first access if
  none exists, which a "writes nothing" dry-run command must never trigger.
  No project found → "No entities to consolidate against (project not yet
  initialized)" and return, without ever touching `.project_id`. New test
  confirms zero rows in `projects` both before and after a dry run against a
  freshly-`init`'d (never-ingested) project.
- `docs/config.md`'s `[consolidation]` block now names `callmem consolidate
  --dry-run` as the tool to run before enabling, ahead of the existing
  `consolidation_log`-review guidance.

## Concerns / judgment calls

- Cluster collapse assumes every connected NOOP/UPDATE component reduces to
  exactly 1 survivor. That's the right first-pass estimate (matches "would
  collapse to 1 of n" as asked) but is not a full order-dependent simulation
  of live consolidation's actual apply sequence — flag if a stronger
  guarantee is wanted for the real calibration sweep tonight; I read
  "estimate" in the ask as licensing this simplification.
- R6's fix is scoped to `httpx.HTTPError` + `json.JSONDecodeError` specifically
  (matching what the two shipped clients can actually leak, and
  `embeddings.py`'s existing precedent) rather than a broader catch — a
  custom third `llm` implementation raising something else entirely would
  still propagate. Flagging in case a wider net was intended, but a broader
  catch would conflict with the "no broad except-Exception" global
  constraint.
- Did not touch repository.py or the extraction.py live-path integration in
  this round — every fix lives in `EntityConsolidator`'s dry-run-specific
  reporting code or `cli.py`, per the reviewer's framing that the mechanism
  itself was already approved.
